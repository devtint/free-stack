Keep-alive

Free tiers save money by putting idle services to sleep. This guide shows how to keep the one service that matters awake, and how to stop Supabase from pausing, without breaking any rules.

Which services sleep

ServiceWhat happensWhenCost of waking
Render free web serviceSpins down15 minutes without inbound trafficAbout a minute on the next request
Supabase free projectPausesAbout 7 days without activityManual restore from the dashboard
Vercel and Cloudflare WorkersNothing to fixFunctions scale to zero but start in millisecondsNone worth worrying about
Stay inside the limits

Render gives each workspace 750 free instance hours a month. That is enough for exactly one service to run all month. If you keep two awake, both stop around day 16 and every free service in the workspace is suspended until the 1st.

Keep only the service that needs it awake, such as a bot webhook. Let demos sleep.

Add a health endpoint

Pingers need a URL that answers quickly. Make one that does no real work, so a ping is cheap and never changes data.

FastAPI
@app.get("/healthz")
def healthz():
    return {"ok": True}
Express
app.get('/healthz', (req, res) => res.json({ ok: true }))

Set the same path as the Health Check Path in Render so deploys also use it.

Option 1: UptimeRobot

The free plan gives you 50 monitors checked every 5 minutes, and it is allowed for commercial projects. You also get email alerts when your service goes down, which is useful on its own.

  1. Create an accountSign up at uptimerobot.com and verify your email.
  2. Add a monitorNew monitor, type HTTP(s). Paste https://your-service.onrender.com/healthz. Interval 5 minutes.
  3. Set up alertsPick your email as the alert contact. You will hear about outages before your users do.
  4. Check it after a dayThe response time chart should show no one-minute wake-up spikes.

Option 2: cron-job.org

A free service that calls a URL on any schedule, down to every minute. It is the most flexible option when you need custom timing or headers.

  1. Create a cronjobSign up, then Create cronjob. Enter your health URL.
  2. Pick the scheduleEvery 10 minutes is plenty for Render, which sleeps after 15.
  3. Turn on failure notificationsJobs are disabled automatically after 25 failures in a row. With notifications on, you get an email when that happens.

Requests time out after 30 seconds. A sleeping Render service can take longer than that to wake, so the very first ping may fail. Once the service is warm, pings succeed.

Option 3: GitHub Actions

A scheduled workflow keeps everything in your repository and costs nothing on public repos.

.github/workflows/keepalive.yml
name: Keep alive
on:
  schedule:
    - cron: "*/10 * * * *"
  workflow_dispatch:

jobs:
  ping:
    runs-on: ubuntu-latest
    timeout-minutes: 3
    steps:
      - name: Ping Render
        run: curl -fsS --retry 3 --retry-delay 20 --max-time 90 "${{ vars.HEALTH_URL }}"
Good as a backup, not the only pingerThe shortest schedule is every 5 minutes, runs can be delayed when GitHub is busy, and public repositories disable schedules after 60 days of no activity. Pair it with UptimeRobot or cron-job.org.

Keep Supabase from pausing

Supabase looks at real activity. A request that touches the database is the reliable way to count. Create a tiny table that anyone can read, then query it a few times a week.

SQL Editor
create table public.heartbeat (id int primary key, note text);
insert into public.heartbeat values (1, 'ok');

alter table public.heartbeat enable row level security;
create policy "Public read heartbeat" on public.heartbeat
  for select to anon using (true);
.github/workflows/supabase-heartbeat.yml
name: Supabase heartbeat
on:
  schedule:
    - cron: "23 6 */2 * *"     # every second day at 06:23 UTC
  workflow_dispatch:

jobs:
  ping:
    runs-on: ubuntu-latest
    steps:
      - run: |
          curl -fsS "${{ vars.SUPABASE_URL }}/rest/v1/heartbeat?select=id" \
            -H "apikey: ${{ secrets.SUPABASE_PUBLISHABLE_KEY }}"

If your app has real users every few days, you do not need this. If the project does pause, open the dashboard and choose Restore. Paused projects can be restored for up to a year.

Option 4: a Cloudflare cron Worker

If you already use Cloudflare, a Worker with a Cron Trigger is very reliable and does not depend on GitHub. One Worker can ping several URLs. Setup is in the Cloudflare guide.

Troubleshooting

Service still sleeps even though pings succeed

Check the pinger hits the public onrender.com URL or your custom domain, not an internal one. The interval must be under 15 minutes.

All free services stopped mid-month

The workspace ran out of 750 instance hours because more than one service was kept awake. Remove extra monitors.

The GitHub keep-alive workflow stopped

Schedules are disabled after 60 days without repository activity in public repos. Re-enable it in the Actions tab.
