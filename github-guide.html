Set up a repository

Create the repository on GitHub, then push your local project (see the Git guide). These files make it easier for you and others to work with:

FileWhy
README.mdWhat it is, how to run it, how to deploy it
.gitignoreKeeps dependencies, builds and secrets out
.env.exampleLists the variables the app needs, with fake values
LICENSEWithout one, nobody can legally reuse your code. MIT is a common choice.
.github/workflows/Your CI and automation

Turn on the safety features

In Settings, Advanced Security (Code security on some accounts), enable secret scanning and push protection. Push protection blocks a push that contains a recognised API key before it ever reaches GitHub.

Work through pull requests

Even alone, opening a pull request for each change is worth it: CI runs on it, Vercel and Render post preview links, and you get a readable record of why things changed.

  1. Branch and pushgit switch -c fix/login, commit, git push -u origin fix/login.
  2. Open the pull requestGitHub shows a banner after the push. Write what changed and why. Writing Closes #12 in the description closes that issue on merge.
  3. Wait for checksTests and preview deployments report back on the pull request.
  4. MergeSquash and merge keeps one tidy commit per pull request on main. Delete the branch afterwards.

GitHub Actions basics

A workflow is a YAML file in .github/workflows/. It says when to run (events), where (a runner) and what (steps).

.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-node@v7
        with:
          node-version: 22
          cache: npm

      - run: npm ci
      - run: npm run lint
      - run: npm test

Python version

.github/workflows/ci.yml
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.12", "3.13"]
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: ${{ matrix.python-version }}
          cache: pip
      - run: pip install -r requirements.txt
      - run: pytest

Save minutes

  • Use cache: on the setup actions so dependencies are not downloaded on every run.
  • Skip runs for documentation-only changes with paths-ignore: ["**.md"] under the event.
  • Cancel superseded runs when you push again quickly:
YAML
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

Secrets and variables

Add them in Settings, Secrets and variables, Actions. Secrets are encrypted and masked in logs. Variables are for non-sensitive settings.

YAML
steps:
  - run: ./deploy.sh
    env:
      API_TOKEN: ${{ secrets.API_TOKEN }}
      APP_ENV: ${{ vars.APP_ENV }}
  • Secrets are not passed to workflows triggered by pull requests from forks, so outsiders cannot steal them.
  • Give each workflow the least access it needs with a permissions: block, for example contents: read.
  • Prefer pinning third-party actions to a full commit SHA rather than a tag. Tags can be moved; SHAs cannot.

Scheduled workflows

The schedule event runs a workflow on a cron expression. It is handy for keep-alive pings, nightly backups and reports.

.github/workflows/nightly.yml
on:
  schedule:
    - cron: "17 3 * * *"     # 03:17 UTC every day
  workflow_dispatch:          # adds a "Run workflow" button
Know the scheduling rules

The shortest interval is every 5 minutes. Times are in UTC. Runs can be delayed or dropped when GitHub is busy, especially at the top of the hour, so choose an odd minute like 17.

Schedules only run on the default branch, and in public repositories they are disabled automatically after 60 days with no repository activity. GitHub emails you before that happens.

GitHub Pages

Pages hosts static sites for free from a public repository at username.github.io/repo, with HTTPS and optional custom domains.

Plain HTML

In Settings, Pages, choose Deploy from a branch, pick main and the root folder. This site works exactly like that.

Built sites (Vite, Astro, Next.js static export)

Choose GitHub Actions as the source, then add a workflow that builds and uploads the output folder:

.github/workflows/pages.yml
name: Deploy Pages
on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
          cache: npm
      - run: npm ci && npm run build
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v4
        with:
          path: dist
      - id: deployment
        uses: actions/deploy-pages@v4

A site served from /repo/ needs its base path set, for example base: '/repo/' in vite.config.ts. Otherwise CSS and JavaScript load from the wrong URL.

Protect your main branch

Rulesets (Settings, Rules, Rulesets) replace classic branch protection and can target several branches at once. A sensible solo setup for main:

  • Require a pull request before merging, with zero required approvals, so every change goes through CI.
  • Require status checks to pass, and select your test job.
  • Block force pushes and restrict deletions.

Rulesets are available on public repositories with the free plan. For private repositories some rules need a paid plan.

Dependabot

Dependabot opens pull requests when your dependencies have security fixes or new versions. Enable alerts and security updates in Settings, then add a config for regular version updates:

.github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: "/"
    schedule:
      interval: weekly
    groups:
      minor-and-patch:
        update-types: ["minor", "patch"]
  - package-ecosystem: github-actions
    directory: "/"
    schedule:
      interval: monthly

Grouping minor and patch updates turns a dozen small pull requests into one.

Troubleshooting

Workflow does not run at all

Check the file is in .github/workflows/ on the branch that received the event, and that the YAML is valid. The Actions tab shows parse errors.

Scheduled workflow stopped running

In a public repo with no activity for 60 days, schedules are disabled. Re-enable it from the Actions tab, or make a commit.

"Resource not accessible by integration"

The workflow's GITHUB_TOKEN lacks a permission. Add it in a permissions: block, for example pull-requests: write.

Pages shows a 404 or unstyled page

Check the Pages source setting, that an index.html exists in the published folder, and the base path for project sites.
