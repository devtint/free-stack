Render

Run an always-listening backend, such as an API or a webhook bot, without managing a server. This guide covers setup, the free instance's limits and how to work with them.

What you get

Render runs your code as a web service on a container it builds from your Git repository. You can deploy Python, Node.js, Go, Ruby, Rust, Elixir or any Dockerfile. Each service gets an onrender.com URL with HTTPS.

The free instance is meant for hobby projects and testing. Render itself says not to use it for production. The trade-offs are clear and easy to plan around:

LimitFree instance
Instance hours750 per workspace per month. Enough for one service running all month. Sleeping services use none.
Spin-downAfter 15 minutes with no inbound HTTP requests or WebSocket messages
Spin-upAbout one minute on the next request
DiskEphemeral. Files you write are lost on redeploy, restart or spin-down
Not availablePersistent disks, scaling, SSH and shell access, one-off jobs, outbound SMTP ports 25, 465 and 587
Free Postgres1 GB, one per workspace, expires 30 days after creation (14-day grace period, then deleted)
Free Key ValueIn memory only, data is lost on restart
Use Supabase for your databaseRender's free Postgres is deleted after 30 days. For anything you want to keep, put the data in Supabase and use Render only for compute.

Create a web service

  1. Connect your repositoryIn the dashboard choose New, Web Service, and connect GitHub or GitLab. Pick the repository and branch.
  2. Choose the runtime and regionRender guesses the language. Pick the region closest to your database or users.
  3. Set the build and start commandsSee the table below for common stacks.
  4. Choose the Free instance typeUnder Instance Type, select Free.
  5. Add environment variablesAdd your secrets now. You can also upload whole secret files, such as a .env or a credentials JSON.
  6. DeployWatch the logs. When you see the service is live, open the URL. Later pushes to the branch redeploy automatically.

Bind to the right port

Render sets a PORT environment variable (default 10000) and expects your app to listen on 0.0.0.0 at that port. Listening on localhost or a hard-coded port is the most common reason a first deploy fails with "no open ports detected".

server.js
const port = process.env.PORT || 3000
app.listen(port, '0.0.0.0', () => console.log(`listening on ${port}`))
main.py
import os
import uvicorn
from fastapi import FastAPI

app = FastAPI()

@app.get("/healthz")
def health():
    return {"ok": True}

if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=int(os.environ.get("PORT", 8000)))

Gunicorn reads PORT automatically on Render, so gunicorn app:app works without a bind flag.

Environment variables and secret files

  • Set variables in the service's Environment tab, or share a set across services with an Environment Group.
  • Saving a change triggers a redeploy, so the new value is live within a minute or two.
  • Secret files are mounted at /etc/secrets/<filename> and also placed in your app's root folder.
  • Pin your Python version with a PYTHON_VERSION variable or a .python-version file, and your Node version with NODE_VERSION or engines in package.json.

Render also provides variables you can read at runtime, such as RENDER_EXTERNAL_URL (your public URL, handy for registering webhooks) and RENDER_GIT_COMMIT.

Health checks and zero-downtime deploys

Set a Health Check Path in the service settings, for example /healthz. Render waits for it to return a 2xx or 3xx status before switching traffic to a new deploy, and restarts the service if it keeps failing. Keep the endpoint fast and free of side effects.

Dealing with spin-down

A sleeping free service takes about a minute to answer the first request. You have three options:

  1. Accept itFine for demos and personal tools. Show a friendly loading state in your frontend.
  2. Keep one service awakePing it every 10 to 14 minutes. 750 hours covers exactly one always-on service. Two always-on services would run out around the middle of the month, and then all your free services stop until the 1st. Setup is in the keep-alive guide.
  3. Upgrade that one serviceThe smallest paid instance never sleeps and adds persistent disks and shell access.
Pinging does not fix the diskRender can restart free services at any time, and the filesystem is wiped when it does. Store uploads in Supabase Storage or Cloudflare R2, and state in a database.

Infrastructure as code with render.yaml

A Blueprint describes your services in a file in the repo, so you can recreate the setup in one click. Add render.yaml at the repository root, then choose New, Blueprint in the dashboard.

render.yaml
services:
  - type: web
    name: my-api
    runtime: python
    plan: free
    region: frankfurt
    buildCommand: pip install -r requirements.txt
    startCommand: uvicorn main:app --host 0.0.0.0 --port $PORT
    healthCheckPath: /healthz
    autoDeployTrigger: commit
    envVars:
      - key: PYTHON_VERSION
        value: "3.12.7"
      - key: SUPABASE_URL
        sync: false          # asked for once when you create the Blueprint
      - key: SUPABASE_SECRET_KEY
        sync: false
      - key: WEBHOOK_SECRET
        generateValue: true  # Render creates a random value

autoDeployTrigger can be commit (deploy every push), checksPass (wait for your CI checks to pass) or off.

Deploy hooks and CI

Each service has a secret Deploy Hook URL in its settings. A POST request to it starts a deploy. That lets you turn off auto-deploy and deploy from GitHub Actions only after tests pass:

.github/workflows/deploy.yml
name: Test and deploy
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt && pytest
      - run: curl -fsS -X POST "${{ secrets.RENDER_DEPLOY_HOOK }}"

The simpler alternative is autoDeployTrigger: checksPass, which waits for your GitHub checks without a hook.

Troubleshooting

"No open ports detected" or the deploy times out

Your app is not listening on 0.0.0.0:$PORT. Check the start command and the host your server binds to.

Build fails with a missing module

The package is installed on your machine but not listed in requirements.txt or package.json. Recreate the file from a clean virtual environment.

Uploaded files disappear

The free instance has an ephemeral disk. Write files to object storage instead.

Emails will not send

Outbound SMTP ports 25, 465 and 587 are blocked on free services. Use an email API over HTTPS, such as Resend.

All my services stopped before the end of the month

The workspace ran out of its 750 free instance hours. Keep only one service awake, or upgrade the busy one.
